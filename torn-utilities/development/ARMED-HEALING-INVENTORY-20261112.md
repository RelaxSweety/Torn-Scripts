# Armed healing inventory — DEV .102

TU 0.5.42.102-dev / Item Monitor 1.12.52-dev removes the inventory GET immediately before an integrated Snatch and Run healing POST. When arming a run that plans healing/hospitalization or starts hospitalized, TU fetches complete carried inventory and saves the verified slots with that exact armed intent. The existing post-hospitalization consumption-verification GET refreshes that snapshot. Healing selects the user's configured item from this verified snapshot, sends one useItem POST, then performs the existing post-use inventory GET to verify removal and update capacity. Explicit hospital release remains separate evidence; partial healing does not enable Purchase Max.

This moves one network round trip out of the critical healing path. The previous PDA report spent approximately 0.31 seconds on that pre-use read; actual .102 device timing remains to be measured. There is no automatic item use, extra healing attempt, page reload, or new purchase/departure delay. Purchase-only runs with unused saved medical preferences do not acquire a healing-inventory requirement. Hospitalization's existing handler checks remain; its post-use GET supplies the updated healing snapshot.

The saved snapshot contains only slot/item identity and capacity, is bound to build, owner, intent, watch and country, and persists with the run across same-tab navigation. A missing/mismatched snapshot, an observed subsequent native item mutation, a conflicting passive native inventory read, or a recording gap/cleared history prevents cached healing and requires re-arming. There is no fallback pre-heal GET. Snapshot data is invalidated before submission; timeout or failed post-use verification preserves the unresolved-attempt lock. After a verified partial heal, the new post-use snapshot supports the next separately clicked selected item. This uses the last verified inventory; it cannot make that earlier observation atomic with an unobserved change in another session.

Arming waits for the baseline to complete before enabling actions. Cancellation, lost focus or a changed run cannot resurrect an old arming attempt. Existing ledger reconciliation, selected-item IDs/instance checks, numeric slotID POST contract, profile fallback where needed and direct-handler routing remain.

**DEV monitor tools are retained**, per the user's final instruction. The existing activation/stop/report/clear controls and background recording behavior remain. The previously removed Native inventory refresh investigation section stays removed. One native focus event still follows each verified purchase, without waiting for its read requests or delaying departure.
